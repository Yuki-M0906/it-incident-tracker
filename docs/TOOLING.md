# Tooling

Everything around the four application files. None of it ships to users.

## Preview build

`build-preview.ps1` reads the four source files, expands the `include()` scriptlets and the
version placeholders exactly as Apps Script would, and prepends a `<script>` that defines
`google.script.run` as a mock. The mock keeps sample data in memory and implements every
server function the client calls, including validation rules (unique names, last-admin
guard, rack overlap, derived asset-user columns). Unknown function names fall back to a
console warning so a missing mock is obvious rather than fatal.

The result is one self-contained HTML file that opens from disk. It is used for:

- manual testing of UI changes without deploying,
- the regression suites below,
- every screenshot in the user manual.

A test asserts that the set of function names the client calls equals the set the server
defines, and that the mock covers the same set.

## Regression suites

Five scripts drive the preview file in headless Edge over the DevTools protocol
(`puppeteer-core`, no bundled browser). Roughly 100 checks, each one a scenario that once
failed:

| Suite | Covers |
|---|---|
| history | hash navigation, back/forward, detail-page restore, logout clearing history |
| identity | assignee filter vs. operator identity, draft retention, form restore target |
| hardening | duplicate-ticket-on-back, assignee links, subtab sync, session-invalid handling, multi-tab idle |
| members | member flag, last-member guard, rename cascade, legacy-member linking, user add/disable/delete |
| integrity | login-footer version, "me" button, asset-user autofill, employee→asset propagation, after-hours predicate, legacy separation, provisional ids |

They run before every commit. Each script closes the browser, so the runner restarts Edge
between suites.

## Manual generation

The user manual (Word, ~45 pages) is generated by a Node script using the `docx` package:
a small typographic library (fonts, margins, call-out boxes, info tables, code boxes) and
one long content file. A second script drives the preview file to capture 25 screenshots in
a fixed order. Regenerating the manual after a release is therefore mechanical:
rebuild preview → capture → generate. The cover carries "compliant with build X.Y" and is
checked against the version constants.

Two further Word guides document the field tools (below); their version strings are
patched in place.

## Field tools (PowerShell)

Two scripts run on site PCs, outside the web app:

- **Inventory scanner** — a portable SNMP v2c scanner (BER encoding written by hand, no
  dependencies) that sweeps a subnet, classifies devices from `sysDescr` and produces a CSV
  the app imports into a staging sheet. Design points: community string entered as a
  secure string and never logged, refusal to run from network shares or cloud-synced
  folders, formula-neutralised CSV, results preserved if the save step fails.
- **Directory export** — reads the employee directory from Active Directory and produces
  the CSV the app imports. It is **read-only by construction**: LDAP bind and search only,
  pagination, server- and client-side timeouts, no referral chasing, an attribute-mapping
  wizard that saves to a local JSON, and a hard refusal to run as a privileged account or
  from a shared location.

### The read-only auditor

"Read-only" is verified mechanically, not by review. A separate script parses the export
tool with PowerShell's AST and applies an **allow-list**: every command and every .NET
method call must be on a list of known-harmless ones, or the audit fails. Deny-lists were
tried first and abandoned — they are defeated by module-qualified names, `.exe` suffixes,
reflection, storing a property collection in a variable, and `& $variable`. The auditor
has its own regression set: nine bypass patterns that must each be rejected, plus the
real tools that must pass. It runs before every release of the field tools.

## Release checklist (abridged)

1. Bump the three version constants; update the four file headers and the preview
   builder; add a changelog entry.
2. `grep` for version drift across all files.
3. Syntax-check both JavaScript sources with `new Function`.
4. Rebuild the preview; run the five regression suites; run the auditor's test set.
5. Regenerate the manual; patch the field-tool guides.
6. Commit. Paste the four files into the editor (or `clasp push`), run `setupSheet()`,
   deploy a **new version of the existing deployment** (never a new deployment — the URL
   must not change), hard-refresh, check the version on the login screen.
